## 1. What We Are Building

A **multi-tenant telehealth e-commerce demo** — the Bask Health stack clone. It has two jobs:

1. **Learn it properly.** Every line must be explainable from first principles, not copied from a tutorial.
2. **Showcase it in an interview** as evidence of hands-on experience.

### The demo in one sentence

> A clinic owner signs up, which atomically creates their account *and* their clinic tenant. They configure a storefront, manage categories, and add products from a predefined schema. The public site at `/{slug}` and `/{slug}/shop` is generated automatically from that configuration — **one codebase, one database, provable tenant isolation.**

### The two actors

| Actor | Can do | Cannot do |
|---|---|---|
| **Clinic Owner / Admin** | Sign up, configure storefront, manage categories and products | See another clinic's data, ever |
| **Anonymous Consumer** | Browse any public storefront, shop, view product/category pages | Have an account, sign in, or write anything |

There are **no consumer/patient accounts.** Consumers are always anonymous. This is a deliberate scope cut (see `INSTRUCTIONS.md` §5).

### The central claim the whole project defends

> **Tenant isolation is enforced in three independent layers, and any one alone is bypassable.**

| Layer | Mechanism | Purpose |
|---|---|---|
| UI | `requireRole()` in `admin/layout.tsx` | UX — don't render what they can't use |
| API | `hasRole` tRPC middleware | **the actual authorization** |
| Data | PostgreSQL Row-Level Security | integrity backstop if application code has a bug |

The interview line: *"An owner of Cairo Heart hitting `/alexandria-pediatrics/admin` gets redirected by the layout. Curling the tRPC endpoint without a membership gets `403` from `hasRole`. And if a query ever forgot its `tenant_id` filter, RLS returns zero rows anyway."*

## 3. How TypeScript Becomes the Contract

This is the idea the monorepo exists to serve, and it is the single most valuable thing to be able to explain.

**The chain, end to end.** Seven mechanisms cooperate:

```
1.  apps/web/page.tsx writes:  from '@repo/database'
        │                       a package NAME, not a relative path
        ▼
2.  pnpm install created apps/web/node_modules/@repo/database
        │                       as a JUNCTION → packages/database
        │                       THE name becomes a filesystem path
        ▼
3.  the bundler reads that folder's package.json, follows `main`
        │                       → ./src/index.ts   (a .ts file, not .js)
        ▼
4.  turbopack.root = C:\work\multi-tenant
        │                       the resolved path is INSIDE the root.
        ▼
5.  transpilePackages: ['@repo/database']
        │                       overrides "node_modules = prebuilt JS"
        ▼
6.  SWC strips types, compiles schema.ts + relations.ts + drizzle-orm → JS
        ▼
7.  the module joins the graph. Server Component → runs on the server,
           only the resulting HTML ships to the browser.
```

**`tsc --noEmit` runs entirely in parallel**, following the *same* junction (step 2) but never touching steps 3–7. **Type checking and bundling are two independent systems that resolve through the same filesystem link.** That is why task 1.2a proved *types* crossed the boundary and task 1.4 separately proved *values* did.

**The rule:** a dependency change needs **three** things, not one.

| # | Change | Solves |
|---|---|---|
| 1 | `"@repo/database": "workspace:*"` in `apps/web/package.json` | "I don't know what that package is." `workspace:*` ≠ a version number — a version sends pnpm to the public registry. |
| 2 | `turbopack.root` in `next.config.ts` | "The file is outside my filesystem boundary." |
| 3 | `transpilePackages` in `next.config.ts` | "I can see it but won't compile it — `node_modules` is assumed prebuilt." |

Drop (2) or (3) and you get a *different* error. That asymmetry trips people up constantly.

## 4. Instructions We Follow

`INSTRUCTIONS.md` is mandatory and is read before every response. Its substance:

| **D. REVIEW** | **Only when asked or when they report output.** Never force a review they didn't request. |

### The 5-part explanation — mandatory for every concept

| # | Part | Question |
|---|---|---|
| 1 | **WHAT** | What is it? Definition, mental model, tiny analogy |
| 2 | **WHY** | Why do we need it? What breaks without it? |
| 3 | **HOW** | How does it work mechanically? Execution order, data flow |
| 4 | **WHEN** | When do we use it and when do we *not*? Tradeoffs |
| 5 | **SHOW** | Complete code + why each non-obvious line exists |

### Delivery rules

- Complete runnable code, always. Never "implement this yourself."
- Explain **why a file lives where it does** — placement is a design decision.
- Label every deliverable with its exact roadmap number (`1.4`, `2.3`).
- Every task ends with **Definition of Done** (checkable) and **Self-check questions** (understanding, not just working code).
- Commands in order, with **expected output** for each.
- Flag new/unfamiliar things **before** they appear in code.
- Point out security implications unprompted, every time.
- Where multiple valid approaches exist, present the tradeoff and say which we picked and why.

### Hard security invariants

Violating any of these is a bug *regardless of tests passing*.

1. **`tenantId` is NEVER accepted from the client** — not in `input()`, not in the body. Always derived server-side from session + URL and injected by middleware.
2. **Every tenant query filters by `tenantId`.** No exceptions.
3. **Authorization lives in the tRPC middleware chain**, not in components and not in the URL.
4. **Cookies are `httpOnly`, `secure`, `sameSite: 'lax'`.** The session cookie holds an **opaque random id only** — never a role, never a user id, never a JWT payload.
5. **Passwords are hashed with `bcryptjs`.** Never log passwords, session ids, or PHI.
6. **Three independent defense layers**, all demonstrated.
7. **Zod validates input at every procedure boundary.**
8. **Uniqueness is scoped per tenant, not globally.**

### Architecture invariants

- **Dependency direction is one-way:** `apps/web → packages/database`. The reverse is forbidden.
- **Every index must be justifiable by naming the query it serves.** No indexes by habit.
- **Configurable/white-label data → `jsonb`. Queryable data → typed columns.**
- **Server Components by default.** `'use client'` only where interactivity is required.
- **Never judge workspace health by whether a package has `node_modules`.** pnpm is isolated, not hoisted: `apps/web/node_modules/` **must** exist and contain **junctions** into the root's `node_modules/.pnpm` store. The fracture signals are a **nested lockfile** (`apps/web/pnpm-lock.yaml`) or real directories instead of junctions.
- **Do not use `proxy.ts`.** In Next 16 `middleware.ts` was renamed `proxy.ts` and now runs on the Node runtime, which makes it *possible* to hit the DB there and therefore tempting. Don't. Tenant resolution belongs in the tRPC context (3.2) and the layout (5.1).

### Scope guard

**Out of scope — do not add unless explicitly asked:** cart, checkout, payments; consumer accounts; real file uploads; real drag-and-drop builder (use a settings form); appointments, video, prescriptions, EMR; email verification, password reset, invitations.

**Never cut:** the tRPC middleware chain, `tenantId` server-side injection, the atomic signup transaction, the block editor, the README.

### Communication

Straight to the point. No filler, no praise inflation, no ceremony. One topic at a time. **But never hesitate on teaching** — depth over brevity whenever something is genuinely new. Correct the developer immediately when wrong; say plainly when they're right.

**The 1.3 debugging detour is worth remembering.** `pnpm dev` failed with `Could not find the Next.js package`. Root cause chain:

```
no .git  →  Next located the monorepo root via the Git root
         →  with no repo, it concluded apps/web WAS the root
         →  pnpm-workspace.yaml one level up was "outside" → ignored
         →  Turbopack root = apps/web
         →  pnpm's next is a junction resolving to node_modules/.pnpm/... (ABOVE that root)
         →  Turbopack compiles only inside its root → package not found
```

**Turbopack enforces a hermetic build:** files outside its root aren't in its cache, so a build including them wouldn't be reproducible or portable. Fixed by `git init` + explicit `turbopack.root`.

> **The real lesson:** after `git init`, auto-detection *would* have worked by accident. Deleting `turbopack.root` probably still runs fine on this machine. That's the trap — it works for an accidental reason and breaks in a Docker `COPY` without `.git`, a CI cache without VCS metadata, or a teammate's machine. `turbopack.root` makes the boundary **declarative instead of inferred.** Same principle as 0.1: prefer the strategy that gives the same result regardless of environment.

#### The schema as built

```
   tenants ──────┬──────< categories ──────< products
      │           │
      │           └──────< memberships >────── users
      │
      └────── storefronts   (1:1, config jsonb)
```

| Table | Key columns | Notes |
|---|---|---|
| `tenants` | `slug` **unique**, `name` | `UNIQUE(slug)` is global — correct here, a URL must resolve to exactly one clinic |
| `users` | `email` **unique**, `passwordHash` | |
| `memberships` | `tenantId` FK, `userId` FK, `role` enum | **`tenantId` denormalized on purpose** — see below |
| `storefronts` | `tenantId` FK **unique**, `config` jsonb | One config per clinic, DB-enforced |
| `categories` | `tenantId` FK, `slug`, `sortOrder` | **unique `(tenant_id, slug)`** — tenant-scoped |
| `products` | `tenantId` FK, `categoryId` FK **nullable**, `priceCents` int, `details` jsonb | **unique `(tenant_id, slug)`** — tenant-scoped |

**Why `tenantId` is denormalized onto every tenant-owned table** (including `memberships`, which could derive it by join): it is what makes **Row-Level Security** possible in 2.7. An RLS policy can only reference columns *in the row being filtered*:

```sql
CREATE POLICY tenant_isolation ON products
  USING (tenant_id = current_setting('app.tenant_id')::uuid);
```

No join, no recursion. With `WITH CHECK` it also blocks cross-tenant *writes* — you physically cannot insert a product into another clinic. Deriving tenant through joins would make the policy recurse infinitely, and Postgres explicitly forbids it.

**Typed `jsonb`** — `StorefrontConfig` and `ProductDetails` are enforced by `.$type<T>()`. The column is genuinely flexible `jsonb` in Postgres, but TypeScript rejects a mismatched shape before anything reaches the database. Postgres `jsonb` has zero schema enforcement; this closes that gap at compile time.

**Money is `integer` cents, never `float`.** `0.1 + 0.2 === 0.30000000000000004` in IEEE-754.

**`categoryId` is nullable on purpose** — uncategorized products are real. A `NOT NULL` would force a catch-all "Other" category to exist in every clinic. Drizzle infers the nullability, so `db.query.products.findMany({ with: { category: true } })` types the result as `category: Category | null`. The schema decision and the type you get are the same fact, expressed twice.

#### Indexes and the queries that justify them

| Index | Table | Columns | Query it serves | Kind |
|---|---|---|---|---|
| `tenants_slug_key` | tenants | slug | Resolve `/{tenantSlug}` | **Uniqueness rule** |
| `users_email_key` | users | email | Login lookup | **Uniqueness rule** |
| `memberships_tenant_user_uidx` | memberships | tenant_id, user_id | One role per clinic per user | **Uniqueness rule** |
| `memberships_user_id_idx` | memberships | user_id | "Which clinics am I in?" — every authenticated request | Performance |
| `storefronts_tenant_id_key` | storefronts | tenant_id | One config per clinic | **Uniqueness rule** |
| `categories_tenant_slug_uidx` | categories | tenant_id, slug | Category page URL, tenant-scoped | **Uniqueness rule** |
| `categories_tenant_id_idx` | categories | tenant_id | Storefront category nav | Performance |
| `products_tenant_slug_uidx` | products | tenant_id, slug | Product detail URL, tenant-scoped | **Uniqueness rule** |
| `products_tenant_active_idx` | products | tenant_id, is_active | Shop page — hottest query | Performance |
| `products_category_id_idx` | products | category_id | Category page + shop filter | Performance |

**The distinction that matters most:** a **constraint** is a correctness rule the DB enforces; an **index** is a performance structure that only *helps* a query. Five of the above are constraints. An index merely helps a unique constraint — the reverse is false.

**Why `(tenant_id, is_active)` and not `is_active` alone:** a boolean is ~50% true, so an index on it alone matches half the table and Postgres correctly ignores it. Leading with `tenant_id` makes the predicate selective. **Postgres can only use a *leading* column of a composite index** — `(a,b)` serves `a` and `a AND b`, but not `b` alone. That single fact explains most index mistakes.

**Why tenant-scoped `UNIQUE`s:** Clinic A and Clinic B must both be able to have a category called "Pain Relief" — different tenants, one shared slug space. A bare `UNIQUE (slug)` would be a genuine multi-tenant bug.

### Next task: **Phase 2.5 — `db.ts`**

The Postgres client. Three non-obvious pieces, all of which exist to prevent a failure that is *silent* when it happens:

1. **`prepare: false`** — postgres.js defaults to prepared statements, which break behind PgBouncer in transaction mode. Every serverless Postgres (Neon, Supabase, Vercel Postgres) sits behind one. Learn it now, save a 3-hour debug later.
2. **`globalThis` caching** — without it, every dev hot-reload allocates a fresh connection pool and leaks it, until Postgres refuses connections. You hit this within ten minutes of normal dev if you skip it.
3. **The `server-only` guard** — turns a silent security failure into a loud one.

#### The `server-only` design conflict, and why the obvious approach is wrong

`server-only` is a package that **throws** when imported outside a React Server Component. Its `package.json` uses the `react-server` export condition: Next's server build gets a no-op `empty.js`, anything else gets `index.js` which throws.

**The trap:** the **seed script (2.6) runs under `tsx`, not Next** — so `react-server` is *not* set, and a naive `import 'server-only'` inside `db.ts` would make seeding throw on startup.

**Resolution — guard the public entry point, not the module:**

| File | Contents | Guarded? |
|---|---|---|
| `db.ts` | The client. `postgres()` + Drizzle | **No** — so tooling can import it |
| `index.ts` | `import 'server-only'` + `export * from './db'` | **Yes** |
| `seed.ts` (2.6) | Imports `./db` **directly**, bypassing the barrel | No |

Net effect: a Client Component importing `@repo/database` hits `index.ts` → `server-only` → error. The seed script imports `db.ts` → fine.

**Why this matters at all:** `index.ts` is a barrel (`export *`). Once `db.ts` exists, a single `"use client"` component importing *anything* from `@repo/database` drags in `db.ts`, which reads `process.env.DATABASE_URL`. The failure mode isn't a crash — it's a **build that succeeds while shipping your connection string to every visitor.** Nothing errors; you only find out by inspecting the output.

#### 2.5 verification — a negative test

Add `"use client"` to `app/page.tsx`, run `pnpm build`, and **report the exact error.** I genuinely don't know whether Turbopack surfaces this at build time or at render time, and for a security boundary *where* it fails is the thing worth knowing rather than assuming. That is a real experiment, not a formality.

**Fallback if `server-only` misbehaves with Turbopack:** grep the client output for the connection string — `Select-String -Path ".next\static\**\*.js" -Pattern "postgres://"`. It must return nothing.
